# План: отдельный поток для записи аудио

Дата: 2026-07-23
Статус: **заменён на VAD-подход** (2026-07-23)

## Анализ проблемы

**Симптом:** аудио записывается с замедлениями, не в реальном времени.

**Причина:** `backgroundWorker` — единственная горутина на CSV + MP3.
MP3-кодирование через go-lame (CGo) — CPU-тяжёлая операция.
Пока горутина занята кодированием, новые аудио-фреймы накапливаются
в канале и дропаются при переполнении.

## Итоговое решение (VAD вместо audioWorker)

**Анализ пользователя:** «записываем мы речь, для неё не нужна такая пропускная
способность. Не записываем пустоту и шумы — только речь.»

**Корень проблемы:** пишем ВСЁ аудио (речь + тишина + шум). 95% времени — тишина,
которая бессмысленно грузит MP3-кодировщик.

**Решение:** Voice Activity Detection (VAD) на входе логгера — фильтруем тишину,
пишем только речь. Объём данных падает на порядок, bottleneck исчезает.

**Реализовано в `internal/logger/session.go`:**
- Добавлен VAD-гистерезис: 3 фрейма речи для старта, 10 фреймов тишины для остановки
- Порог амплитуды: 500 (из 32767, ~1.5% от максимума)
- Функция `vadPass(pcm)` — решает, писать фрейм или нет
- Функция `hasSpeech(pcm, threshold)` — проверка по пиковой амплитуде

**Результат:**
- Аудио-файлы содержат только речь (без пауз и шумов)
- Размер MP3: ~8.8% от raw PCM (подтверждено тестом)
- Никаких дополнительных горутин — `backgroundWorker` справляется одна
- Все 17+17 тестов (`logger` + `pipeline`) проходят

```
                     │ (только PCM-фреймы)  │  │ ┌──────────────┐ │
                     └──────────────────────┘  │ │ batch (N фр) │ │

                                                │ │ lame.Write   │ │
                                                │ └──────────────┘ │
                                                └──────────────────┘
```

**Ключевые изменения:**
1. `audioWorker` — отдельная горутина
2. `SaveAudioChunk` → пишет в `audioCh`, не в `writeCh`
3. Reusable buffers в audioWorker
4. Batch encoding
